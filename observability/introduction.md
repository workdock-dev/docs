# Observability

WorkDock is instrumented at its core and natively exports telemetry through **OTLP (OpenTelemetry Protocol)**. Because the telemetry is OTLP-native, WorkDock can integrate with virtually any OTLP-compatible observability platform, including SigNoz, Grafana, Jaeger, and Honeycomb.

## Why it matters

When AI agents are performing work on your behalf, understanding **what is happening inside the orchestration engine** becomes just as important as the work itself.

WorkDock emits metrics and traces across the major stages of the workflow — from job scheduling and agent sessions to tool calls, token usage, model selection, cost, and execution results. This gives you a real-time view of how work moves through the system and makes it easier to identify bottlenecks, failures, unexpected behavior, and cost patterns.

WorkDock includes **two built-in dashboards** for monitoring these metrics and also collects distributed traces that let you follow a job across the entire lifecycle:

**Issue Assignment → Job Scheduling → Sandbox Provisioning → Agent Session → Tool Execution → Pull Request**

## Task Scheduler Metrics

The task scheduler emits metrics under the `workdock.task_scheduler` meter. These metrics provide visibility into worker utilization and job execution.

| Metric                   | Type      | Unit       | Description                           |
| ------------------------ | --------- | ---------- | ------------------------------------- |
| `scheduler.worker.total` | Gauge     | `{worker}` | Total number of workers in the pool   |
| `scheduler.worker.busy`  | Gauge     | `{worker}` | Workers currently processing a job    |
| `scheduler.worker.idle`  | Gauge     | `{worker}` | Workers idle and waiting for work     |
| `scheduler.job.duration` | Histogram | `ms`       | Time a worker takes to complete a job |
| `scheduler.job.count`    | Counter   | `{job}`    | Jobs processed by the task scheduler  |

Job count and duration metrics include attributes that help explain the outcome of each job:

* **`job.result`** — `succeeded`, `failed`, `retry`, or `cancelled`
* **`job.error_type`** — The categorized error type, such as `ErrBadRequest`, `ErrHarnessUnhealthy`, or `ErrGitHubConnectionReRequested`

The scheduler also produces spans for key stages of job execution:

`job.execute` → `job.claim` →  `job.handler` → `job.complete`

Failure and retry paths are represented by `job.fail` and `job.retry`. Heartbeat events are also emitted during execution to provide visibility into worker liveness.

## Service Metrics

WorkDock's AI service emits spans under the `workdock.ai_service` tracer, covering the lifecycle of an agent session.

Key operations include:

* **`session.get_event`** — Retrieves a session event.
* **`session.get`** — Looks up an existing session.
* **`session.process`** — Processes the session and coordinates the next stage of execution.

The `session.process` span includes attributes such as `session.organization.id`, `session.identifier`, `session_event.identifier`, and `session.provider`.

These traces connect the initial issue-tracker webhook to session processing and, ultimately, harness execution, providing visibility across the transition from **work request to agent execution**.

## OpenCode Metrics

The OpenCode harness provides more detailed telemetry around AI execution under the `opencode` meter. These metrics expose what the agent is doing, which models it is using, how many tokens it consumes, and how much each session costs.

| Metric                         | Type      | Unit          | Description                        |
| ------------------------------ | --------- | ------------- | ---------------------------------- |
| `opencode.session.count`       | Counter   | `{session}`   | Sessions created                   |
| `opencode.token.usage`         | Counter   | `{token}`     | Tokens consumed by type            |
| `opencode.cost.usage`          | Counter   | `USD`         | LLM cost incurred                  |
| `opencode.tool.duration`       | Histogram | `ms`          | Tool execution duration            |
| `opencode.tool.count`          | Counter   | `{call}`      | Tool calls executed                |
| `opencode.session.duration`    | Histogram | `ms`          | Session duration                   |
| `opencode.message.count`       | Counter   | `{message}`   | Completed assistant messages       |
| `opencode.session.token.total` | Histogram | `{token}`     | Total tokens consumed by a session |
| `opencode.session.cost.total`  | Histogram | `USD`         | Total cost of a session            |
| `opencode.model.usage`         | Counter   | `{message}`   | Messages generated by model        |
| `opencode.retry.count`         | Counter   | `{retry}`     | API retries                        |
| `opencode.cache.count`         | Counter   | `{operation}` | Cache operations                   |

Token usage is broken down by type, including **input, output, reasoning, cache read, and cache creation** tokens.

Common attributes across these metrics include:

* **`gen_ai.request.model`** — The model used, such as `claude-3`
* **`gen_ai.provider.name`** — The model provider, such as `anthropic`
* **`gen_ai.operation.name`** — The type of AI operation
* **`tool`** — The tool being executed
* **`success`** — Whether the tool call completed successfully

OpenCode also produces spans under `workdock.gen_ai` and `workdock.opencode`, covering important stages such as session creation, agent invocation, and event/chunk parsing.

## Traces

Metrics tell you **what happened**; traces show you **how it happened**.

WorkDock collects distributed traces across the orchestration pipeline, allowing you to follow a single job from the moment it enters the scheduler through the different services and integrations involved in its execution.

A typical trace can connect:

**Scheduler → AI Service → Linear/GitHub → Sandbox → OpenCode → Tool Calls → Pull Request**

Because these traces are exported through OTLP, they can be consumed by the observability platform of your choice. This makes it possible to move from a high-level dashboard showing system health and agent activity into an individual trace and understand exactly where time was spent, what operations were performed, and where a job may have failed.

The result is observability across both sides of the system: **WorkDock's orchestration layer and the AI agent's execution layer**.
